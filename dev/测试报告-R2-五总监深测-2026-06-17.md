# NexusAPI 企业管理平台 · 第二轮·五总监独立深度测试报告（R2）

- 测试时间:2026-06-17
- 环境:本机容器栈(平台 18080 + new-api rc.4 13000 + MySQL),全 MOCK,**任何请求未打线上**
- 方式:**5 个角色各用各自不同的测试方法独立跑、互不商量**,最后交叉印证汇总
- 被测构建:容器 `nexus-ent-dev`,`readyz milestone=6-feature-complete`

> 与 R1(单人一遍过)的区别:R2 是名副其实的多视角——产品(黑盒走旅程+截图)/研发(白盒读码+数据层+并发压测)/测试(系统化对抗矩阵)/商务(逐笔三层对账)/运维(故障注入+恢复演练)。**5 路各自挖到了 R1 漏掉的问题**,证明深度多视角是必要的。

## 一、总体结论

**有条件通过。核心可信,但对客商用/上生产前有一批必修项。**

- **可信的内核(各路一致确认达标/优秀)**:权限与租户隔离、认证防伪、动钱的幂等/并发安全、折扣数学、明文凭证不泄露、零侵入摘除(平台全停网关零感知)、故障秒级自愈。
- **必修的短板**:退款对账闭环破、折扣并发写无锁、就绪探针不探 DB、成员页/列表 UI 缺陷、折扣无前端入口、对外缺币种字段、输入校验与 HTTP 码口径。

### 各维度判定

| 维度 | 判定 | 一句话 |
|---|---|---|
| 产品 / UX | 有条件达标 | 主旅程顺、AC 达标;成员空白卡 / 长名破版 / 折扣无入口须先修 |
| 研发 / 实现 | 达标(健壮性差 1 处) | 折扣数学/合并保留/零侵入对;**折扣并发写无锁需修** |
| 测试 / 质量 | 权限认证并发优秀;边界基本达标 | RBAC/隔离/认证/幂等满分;输入卫生(长串 500、调额无上限)需补 |
| 商务 / 计费 | 计费内核达标;**可对账性不达标** | 数值逐笔精确;退款污染累计充值、无退款流水、对外无币种 |
| 运维 / SRE | 韧性优秀;可用性基本达标 | 自愈/零侵入摘除满分;**readyz 不探 DB**、缺资源限制/metrics |

## 二、严重项(必修,阻塞对客/生产)

| # | 维度 | 问题 | 证据 | 建议 |
|---|---|---|---|---|
| S1 | 商务 | **退款冲正污染"累计充值"+ 无独立退款流水** | 冲正 5M 后 `company_balance.total_recharged` 50M→45M,但不可变 `recharge` 流水仍 50M,两表差额=退款额;退款唯一留痕在 audit_log | 冲正只减 balance、不动 total_recharged;落独立 refund/debit 流水表,保"充值−退款−消耗=余额"恒等 |
| S2 | 研发 | **配折扣 `GroupGroupRatio` 读-改-写无锁,并发丢更新(动钱)** | `adapter/newapi/options.go:41 SetGroupGroupRatio`、`service/pricing.go:49` 均无串行化;40 并发实测一个 org 倍率停在旧值 | 用现成 `KeyedLocker` 给 option 读-改-写包全局键锁(键如 `option:GroupGroupRatio`)。**这正是 G 类"平台内部单写者"那层,代码里在折扣路径上缺失** |
| S3 | 产品 | 成员「我的用量」3 张 KPI 卡**空白** | `app.js:332` 硬编码 `kpi("","","")×3`,结构性;成员首屏像没做完 | 填实(配额上限/剩余/到期)或去掉占位只留 1 张 |
| S4 | 产品 | 客户组织列表**长名撑爆表格** | 几十字符组织名横贯整行无省略号,破版 | 加 `text-overflow:ellipsis`+max-width(并配 S7 服务端长度校验) |
| S5 | 运维 | **/readyz 静态探针,不探 DB** | 停 MySQL 后 readyz 仍 `ready`,但库操作全 500;LB/编排会继续打流量 | readyz 真探一次 `db.Ping()`(+可选探上游) |

## 三、一般项(影响运营/出账/可观测,建议本轮修)

| # | 维度 | 问题 | 建议 |
|---|---|---|---|
| M1 | 产品 | **折扣/定价无前端入口**——后端 `PUT /pricing` 能用,运营方界面找不到配折扣的地方(我们设计的 A1/A2 折扣未触达用户) | 在组织详情加折扣配置 UI(整体/按分组),客户侧只读 |
| M2 | 商务 | 余额/账目对外只返 raw quota,**无币种/金额展示字段**($100 是前端自己折算的,有币种歧义) | 响应补 `currency:"USD"`+`amount_display`,口径固化在后端(对应 A3/A4) |
| M3 | 测试 | 超长字符串字段(>~190)落 DB 列溢出 → **500**(应 400/422) | handler 层补字段长度上限校验 |
| M4 | 测试 | 调额 `delta_quota` 缺失/null **仍建 grant**;超大值(1e17)无上限 | 必填非空校验 + 数值上限(动钱面) |
| M5 | 产品 | 审批列表不显示**申请人/时间**;`created_at` 是 `0001-01-01` 脏值 | 补申请人+真实时间(审批要担责) |
| M6 | 产品 | 无任何**待办角标**(badge-dot 定义了但 app.js 没用):管理员看不到"1 待审"、成员看不到未读红点 | 接上 unread/pending 计数角标 |
| M7 | 产品 | 管理员本人混入「成员」列表且带"停用"按钮 | 管理类账号不进成员列表/不给自停入口 |
| M8 | 产品 | 层级列表缺「月额度」列,无改/删层级 | 补列 + 编辑/删除 |
| M9 | 运维 | **50301(上游鉴权失效)走 HTTP 200 包 body code**,其余故障都用 5xx,口径不一致,按 HTTP 状态告警会漏 | 50301 也返 5xx(或 401/403) |
| M10 | 运维 | 容器无资源限制(Memory=0/Cpus=0)、重启策略 `no` | 生产设 mem_limit/cpus + `restart: unless-stopped`(参考线上 2核2G) |

## 四、轻微 / 建议

- [研发] merge-preserve 与退款冲正缺回归测试(核心铁律没被测试守住)。
- [研发+商务·交叉] `mode=none` 是写回 base=1 而非删键,option 会堆死键(无害,建议删键)。
- [测试] slug/admin_email 不校验格式(建无法登录的管理员);low_watermark 收负值;业务错误返 400 但规格 §0.2 写 422,口径要统一。
- [产品] 成员合成邮箱当登录名不直观;通知用 emoji 🔔 与其余单色图标不一致(且本项目有 emoji 乱码前科);运营方搜索框无 placeholder;`_operator/平台运营方`伪组织混在客户列表;无脏数据归档/清理。
- [运维] 无 /metrics、无告警端点;缺每请求访问日志(响应有 request_id 但日志侧没对上)。
- [商务] recharge-request 必填 type(topup/refund)但 PRD 未提,补文档。

## 五、交叉印证亮点(不同方法独立撞同一处 = 高可信)

- **`mode=none` 不删键**:研发(白盒读码)+ 商务(对账)独立指出。
- **HTTP 码口径不统一**:测试(400 vs 规格 422)+ 运维(50301 走 200)从两头撞到同一类问题。
- **输入长度/校验缺失**:测试(超长串 500)与产品(长名破版 S4)同根。
- **对外缺币种**:商务(API 无币种字段)与产品(余额展示)指向同一缺口。

## 六、各路一致确认的强项(达标/优秀)

- **权限/隔离/认证(测试:优秀)**:RBAC 矩阵 100% 合规;跨 org 一律 404 无 IDOR;支持会话后端闸;**自签 `role:ops` 提权被拒 401**。研发、商务从各自角度复证(动钱仅运营方)。
- **动钱幂等/并发安全(测试+研发)**:20 并发同 transfer_no = 1 成功 + 19 个 409、余额精确;余额 `FOR UPDATE`+乐观锁+守恒断言;无重复扣。
- **折扣数学(研发+商务)**:abs=base×pct 覆盖式逐档(0.8/0.7/1)一致;**外来 `vip` 键并发 40 写后存活**(merge-preserve 成立)。
- **零侵入摘除(运维+研发)**:平台全停时 new-api 网关 50并发×100 全 200、版本正常=客户零感知;平台只写 `GroupGroupRatio` 一个 option,不碰库/缓存。**铁律守住。**
- **凭证不泄露(运维+研发+产品+测试)**:明文 key/密码不入库、不入日志、不进 audit detail、不回列表;日志 grep 0 泄露;凭证经 env 注入不落盘。
- **韧性自愈(运维)**:上游停=写退避后明确报错、库停=500 不崩,依赖恢复后均**秒级自愈、零人工、0 panic**;50301 有 `run-server.sh` 重 bootstrap runbook 已跑实。

## 七、给开发的修复优先级

1. **先修 5 个严重项**:S1 退款流水+不污染累计充值、S2 折扣并发加锁、S5 readyz 探 DB、S3 成员空白卡、S4 长名截断。
2. **再清一般项**:M1 折扣前端入口、M2 对外币种字段、M3/M4 输入校验、M9 HTTP 码统一、M10 生产资源限制/重启策略;M5–M8 运营效率类 UI。
3. **补回归测试**:merge-preserve、退款冲正、并发折扣(把这次实测出的并发丢更新做成用例,防回归)。
4. 轻微/建议项随手清。

## 八、环境状态

运维演练后**已完整复原**:三容器全 Up(mysql healthy)、`/readyz`=ready、`/healthz`=ok、new-api `/api/status`=200、`mysqladmin ping`=alive。数据为基线 + 各路 `prod-/eng-/qa-/biz-/sre-` 前缀测试组织,无污染无损坏;如需清场 `bash dev/reset.sh` 还原 new-api 侧 + 按需清平台库测试组织。

## 结论

**核心架构、安全、钱的算法、零侵入、韧性——可信且达标。** 但"对外出账/对账、折扣可操作性、就绪探针、UI 完成度、输入卫生"这几块还不到对客商用/上生产的线。**修掉第二节 5 个严重项 + 第三节关键一般项(尤其 S1/S2/M1/M2),即可进灰度。**
