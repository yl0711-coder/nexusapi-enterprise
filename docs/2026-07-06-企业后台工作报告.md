## 2. 本轮修改背景

之前企业后台功能已经能跑通，但前端体验和信息架构存在明显问题：

- 组织详情页把多个大功能放进弹窗，信息量大时很难操作。
- API Key 归属、请求日志、员工管理等表格列宽混乱，内容换行、重叠、复制按钮位置不稳定。
- 请求日志没有按角色区分字段，员工、组织管理员、运营方看到的字段混在一起。
- 请求日志没有充分对齐 new-api 的使用日志逻辑，用户视角暴露了不该看的字段，比如渠道、token_id。
- 员工“我的用量”图表和 mock 数据显示效果差，费用全是 `$0.00`，无法验收统计效果。
- 运营方缺少全局日志和全局员工/Key 视图，排障不方便。

本轮工作的核心目标是：先把企业后台做成可验收、可交接、可继续迭代的状态，尤其是日志页要学习 new-api 的成熟设计。

## 3. 参考的 new-api 日志逻辑

本轮重点阅读了 new-api v1.0.0-rc.4 里的使用日志实现：

- `web/classic/src/components/table/usage-logs/UsageLogsFilters.jsx`
- `web/classic/src/components/table/usage-logs/UsageLogsColumnDefs.jsx`
- `web/classic/src/hooks/usage-logs/useUsageLogsData.jsx`
- `controller/log.go`

结论如下：

- 普通用户日志接口是 `/api/log/self`。
- 管理员日志接口是 `/api/log/`。
- 普通用户可筛选：时间、令牌名称、模型名称、分组、Request ID、日志类型。
- 管理员额外可筛选：渠道 ID、用户名称。
- 普通用户默认不显示渠道、用户名、重试列。
- 管理员才显示渠道、用户名、重试等排障字段。
- 核心日志列是：时间、令牌、分组、类型、模型、耗时、输入、输出、费用、IP、详情。

企业后台在此基础上做了角色收敛：

- 员工在企业后台等价于一个具体 API Key 使用者，所以员工日志比 new-api 普通用户更窄，不显示令牌、分组、渠道、token_id、成员。
- 组织管理员能管理本组织员工，因此显示成员和令牌，但不显示渠道和 token_id。
- 运营方负责全局排障，因此显示渠道、客户组织、成员、令牌、分组。

## 9. 关键设计说明

### 9.1 启用、禁用、离职的区别

成员状态语义：

- 启用：员工 Key 可用。
- 禁用：临时暂停员工当前 Key，Key 仍保留，可恢复。
- 离职：员工离开组织，Key 失效并进入离职列表；后续恢复时应重新生成 Key 或重新绑定。

前端文案需要避免混淆：

- 禁用用于风控、临时封停、异常排查。
- 离职用于人员退出，语义更重。

### 9.2 可用模型档位的含义

可用模型档位不是 new-api 原生概念，而是企业后台对以下能力的包装：

- new-api 分组
- 可用模型清单
- 企业侧月额度基线
- 员工默认可用范围

创建档位时：

- “计费分组”来自 new-api 可用分组。
- “模型清单”用于企业后台限制/说明该档位可用模型。
- “月额度”是该档位下员工的月额度基线，不是整个组织总额度。

后续需要在 UI 上把这些解释得更直白。

### 9.3 用量统计来源

企业后台目前不是直接实时扫 new-api 日志来渲染所有统计，而是使用本地表：

- `usage_ledger`
- `usage_detail`
- `org_newapi_log`

关系：

- “我的用量”的趋势、按模型排行、最近调用，都应来自同一套用量明细/聚合数据。
- “请求日志”来自 `org_newapi_log`，用于排障，不直接参与扣费。
